# IQwurksPunch 0.9.0

**Release type:** Installation, controlled upgrade, distribution packaging, deployment-template, and administrator-documentation release
**Release version:** 0.9.0
**Release date:** August 5, 2026

---

## Overview

Version 0.9 converts the validated IQwurksPunch production deployment into a repeatable installation, upgrade, packaging, and recovery workflow.

This release adds installation preflight diagnostics, upgrade-readiness checks, read-only upgrade planning, guarded upgrade execution, persistent upgrade journals, interrupted-upgrade assessment, recovery diagnostics, deterministic release packaging, independent archive verification, reusable production deployment templates, and comprehensive installation and upgrade documentation.

The new console workflows are designed to make potentially disruptive operations visible and reviewable before changes are made.

Preview and diagnostic commands remain read-only. Upgrade execution requires explicit confirmation and records its progress so administrators can review completed, failed, or interrupted operations.

Version 0.9 also introduces a versioned distribution archive containing the application source, configuration examples, documentation, deployment templates, and empty runtime directories required for a fresh installation.

Generated packages exclude private configuration, databases, logs, backups, sessions, caches, machine inventories, Git metadata, and Composer-installed dependencies.

This document describes the final Version 0.9.0 release. The release commit, release branch, Git tag, final archive, and published checksum are created after the remaining release-validation steps.

## Highlights

### Installation Preflight Diagnostics

Version 0.9 adds an installation-preflight service and console command.

Run:

```bash
./iqwurks install:check
```

The command evaluates whether the host is ready to install and operate IQwurksPunch.

Checks include:

- Operating-system compatibility
- PHP availability
- PHP version
- Required PHP extensions
- Required system commands
- Application-source availability
- Composer dependency state
- Runtime-directory availability
- Runtime-directory permissions
- Available disk space

The command reports individual PASS, WARN, or FAIL results and provides a summarized readiness result.

Installation checks do not initialize the database, modify configuration, install packages, or change filesystem permissions.

### Upgrade Readiness Diagnostics

Version 0.9 adds upgrade-readiness diagnostics.

Run:

```bash
./iqwurks upgrade:check
```

The command reviews the current installation before an upgrade begins.

Upgrade-readiness checks include applicable items such as:

- Application source
- Installed version
- Runtime directories
- Database availability
- Database readability
- Database integrity
- Pending migrations
- Composer state
- Maintenance-mode state
- Backup readiness
- Upgrade-journal state
- Required system commands
- Available disk space

The command distinguishes blocking failures from warnings requiring administrator review.

A warning does not automatically mean the installation is unsafe. Administrators should review each reported condition before continuing.

### Read-Only Upgrade Planning

Version 0.9 adds a read-only upgrade-plan service and command.

Run:

```bash
./iqwurks upgrade:plan
```

The upgrade plan describes the operations that would be required for the current installation.

The plan can identify expected work such as:

- Readiness validation
- Version comparison
- Maintenance-mode handling
- Backup preparation
- Composer dependency installation
- Database migration execution
- Database validation
- Application-version verification
- Maintenance-mode restoration
- Upgrade-journal recording

Planning does not perform the upgrade.

### Controlled Upgrade Preview

Version 0.9 adds a controlled upgrade preview.

Run:

```bash
./iqwurks upgrade:preview
```

The preview combines upgrade readiness, planning, and operation sequencing into a final pre-execution review.

The preview reports:

- Whether execution is permitted
- Blocking conditions
- Warning conditions
- Planned operations
- Operation order
- Current application version
- Target application version
- Required confirmation phrase
- Whether changes were made

Preview mode is read-only.

### Guarded Upgrade Execution

Version 0.9 adds a guarded upgrade-apply command.

The apply command requires the exact confirmation phrase reported by the preview command.

An upgrade cannot begin from a mistyped, abbreviated, or assumed confirmation.

The controlled execution engine:

- Revalidates upgrade readiness
- Builds the final operation sequence
- Records execution start
- Executes guarded upgrade operations
- Captures operation results
- Stops after a blocking failure
- Records the final execution result
- Preserves failure details
- Reports whether recovery review is required

Potentially disruptive shell commands use argument arrays rather than interpolated command strings.

The process runner bypasses the shell and captures:

- Exit code
- Standard output
- Standard error
- Execution directory
- Timeout status
- Elapsed time
- Success status

### Process Timeouts

Version 0.9 adds controlled process timeouts.

A child process that exceeds its configured timeout is terminated and reported with exit code:

```text
124
```

Timeouts are recorded as operation failures rather than leaving an upgrade command running indefinitely.

### Upgrade Execution Journal

Controlled upgrade execution is recorded in an upgrade journal.

The journal preserves information such as:

- Execution identifier
- Start time
- Completion time
- Initial status
- Final status
- Current version
- Target version
- Planned operation count
- Completed operation count
- Failed operation
- Failure explanation
- Interruption state
- Recovery requirement

Journal records allow administrators to review a prior operation after the original terminal session has ended.

### Upgrade Status

Version 0.9 adds an upgrade-status command.

Run:

```bash
./iqwurks upgrade:status
```

The command reports the most recent controlled upgrade execution and its persisted result.

Status review is read-only.

It can distinguish results such as:

- No recorded execution
- Running
- Completed
- Failed
- Interrupted
- Recovery review required

### Interrupted-Upgrade Assessment

Version 0.9 detects upgrade executions that began but did not record a normal completion.

An interrupted execution may result from:

- Terminal disconnection
- Server restart
- Process termination
- Power interruption
- Unhandled operating-system failure

The interruption assessor uses the recorded journal state rather than assuming that an incomplete operation succeeded or failed safely.

### Upgrade Recovery Check

Version 0.9 adds a recovery-check command.

Run:

```bash
./iqwurks upgrade:recovery-check
```

The command evaluates whether the installation requires recovery review before another controlled upgrade is attempted.

Recovery checks can report:

- No prior upgrade execution
- Prior execution completed normally
- Prior execution failed cleanly
- Prior execution may have been interrupted
- Recovery assessment required
- Upgrade journal unavailable or invalid

The recovery check does not automatically overwrite files, restore a database, or discard journal history.

### Portable Package Manifest

Each Version 0.9 archive contains:

```text
PACKAGE-MANIFEST.json
```

The manifest records package identity and every controlled package entry.

Manifest information includes:

- Manifest schema version
- Application version
- Package base name
- Package filename
- Entry path
- Entry type
- Packaged permission mode
- File SHA-256 digest
- Package-entry totals

The manifest allows an extracted archive to be verified independently of the source checkout that created it.

### Deterministic Package Staging

Version 0.9 adds controlled staging before archive creation.

Staging normalizes filesystem permissions.

Generated runtime directories use:

```text
0770
```

Normal source directories use:

```text
0755
```

Normal source files use:

```text
0644
```

Application entry points use:

```text
0750
```

Executable entry points include:

```text
iqwurks
migrate.php
```

Source ownership and machine-specific permission variations are not copied blindly into the release package.

### Independent Package Verification

Version 0.9 adds independent archive verification.

Run:


```bash

    --archive=storage/exports/packages/iqwurkspunch-0.9.0.tar.gz \

```

Verification checks include:

- Archive readability
- Optional archive SHA-256 match
- Safe archive paths
- Exactly one top-level package directory
- Valid package root
- Valid JSON manifest
- Supported manifest schema
- Package-name consistency
- Archive-filename consistency
- Application-version consistency
- Required installation paths
- Manifest-listed files
- Manifest-listed directories
- File SHA-256 digests
- File permission modes
- Directory permission modes
- Unlisted archive entries
- Empty runtime directories
- Forbidden paths
- Symbolic links
- Temporary-workspace cleanup

The verifier performs extraction in a temporary workspace and removes that workspace after verification.

### Required Installation Paths

Independent verification requires essential installation content, including:

An archive missing deployment documentation is rejected even if its remaining manifest entries are internally consistent.

### Archive Permission Verification

Version 0.9 verifies archived permissions after extraction.

This prevents a release archive from silently converting source directories to world-writable permissions.

Release validation confirms that:

- The package root uses mode `0755`
- Source directories use their expected modes
- Runtime directories use their expected modes
- Normal files use their expected modes
- Application entry points remain executable
- No archive entry is world writable

### Symbolic-Link Protection

Symbolic links are not permitted in IQwurksPunch distribution archives.

This reduces the risk of an extracted package redirecting installation operations outside the intended application directory.

### Safe Archive Paths

Archive entries are rejected when they contain unsafe or invalid paths.

Rejected path forms include:

- Absolute paths
- Empty paths
- Null bytes
- Windows drive-root paths
- Empty path segments
- `.` segments
- `..` segments

## Known Limitations

Version 0.9 does not provide:

- A browser-based installation wizard
- Automatic operating-system package installation
- Automatic Nginx virtual-host activation
- Automatic PHP-FPM template installation
- Automatic firewall-rule installation
- Automatic LightDM or Openbox installation
- Automatic Chromium installation
- Automatic remote release discovery
- Automatic release downloading
- Cryptographic package signing beyond published SHA-256 verification
- Automatic source-code rollback without administrator review
- Cloud-host provisioning
- Multiple-company deployment management
- Multiple-location orchestration
- A universal per-command `--help` option

Deployment templates intentionally contain placeholders and are not installed automatically.

A controlled upgrade still requires:

- A verified backup
- Administrator review
- Correct filesystem permissions
- Correct deployment paths
- Valid configuration
- Sufficient disk space
- A supported runtime environment

The default production deployment continues to use HTTP on a trusted local network. Installations exposed to untrusted networks should use HTTPS and an appropriate reverse-proxy security policy.
