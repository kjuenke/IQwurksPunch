# IQwurksPunch 0.6.0

**Release type:** Backup, recovery, diagnostics, production kiosk, security, and payroll-administration release
**Release date:** July 21, 2026

---

## Overview

Version 0.6 transforms IQwurksPunch from a payroll-preparation application into a production-ready, recoverable, and locally deployed time-clock system.

This release completes the Backup, Recovery, and Diagnostics milestone originally planned for Version 0.6. It also delivers several capabilities that had previously been planned for later releases, including supervisor punch correction, immutable correction history, production web-server deployment, a dedicated physical kiosk, authentication hardening, SQLite WAL mode, offline frontend assets, log rotation, and configurable kiosk inactivity protection.

Version 0.6 is designed for reliable operation on a dedicated Linux computer while remaining accessible to supervisors across the local network.

## Highlights

### Database Backup and Retention

Version 0.6 adds a complete SQLite backup system with:

- Timestamped database backups
- Verified backup creation
- SQLite integrity validation
- Foreign-key validation
- Backup catalog and listing
- Backup retention management
- Preview-only pruning by default
- Explicit deletion mode
- Backup locking
- Automatic daily backup execution
- Backup logging
- Backup failure reporting
- Configurable backup directory
- Configurable retention count

The default configuration stores backups in:

```text
storage/backups
```

The default retention target is:

```text
30 backups
```

The production backup schedule runs daily at 1:15 AM in the company timezone:

```cron
CRON_TZ=America/Los_Angeles
15 1 * * * cd /var/www/IQwurksPunch && /usr/bin/flock -n /tmp/iqwurks-backup-cron.lock /usr/bin/php iqwurks backup:run >> storage/logs/cron-backup.log 2>&1
```

Backup creation uses SQLite’s safe database-copy facilities rather than directly copying the active database file.

This preserves committed data while the application is running in WAL mode.

### Backup Commands

The console application now provides:

```text
backup:create
backup:list
backup:prune
backup:restore
backup:run
backup:verify
```

Examples:

```bash
./iqwurks backup:create
./iqwurks backup:list
./iqwurks backup:verify
./iqwurks backup:verify --all
./iqwurks backup:verify BACKUP_FILENAME
./iqwurks backup:prune --keep=30
./iqwurks backup:prune --keep=30 --delete
./iqwurks backup:run
```

`backup:run` creates a verified backup and safely applies the configured retention policy.

### Safe Database Restore

Version 0.6 adds a guarded database restore workflow.

Restore protection includes:

- Backup filename validation
- Backup integrity verification
- Foreign-key verification
- Preview mode by default
- Explicit `--apply` requirement
- Typed filename confirmation
- Maintenance-mode integration
- Pre-restore safety backup
- SQLite WAL checkpoint handling
- Removal of stale SQLite sidecar files
- Post-restore integrity validation
- Migration-history verification
- Rollback handling if the restore cannot be completed

Preview a restore:

```bash
./iqwurks backup:restore BACKUP_FILENAME
```

Apply a restore:

```bash
./iqwurks backup:restore \
    BACKUP_FILENAME \
    --apply \
    --confirm=BACKUP_FILENAME
```

The confirmation value must exactly match the selected backup filename.

### Supervisor Punch Correction

Version 0.6 adds a complete supervisor punch-correction workflow.

Supervisors can:

- Review an employee’s punch history
- Add a missing punch
- Edit an existing punch
- Delete an incorrect punch
- Specify the punch type
- Specify the punch date and time
- Provide a required correction reason
- Review correction metadata

Supported punch types include:

```text
clock_in
clock_out
break_out
break_in
meal_out
meal_in
```

The correction service validates punch sequencing before committing a change.

Invalid sequences are rejected and rolled back.

### Immutable Punch-Correction History

Every punch correction records an immutable history entry containing the relevant before-and-after information.

Correction history protects payroll accountability by preserving:

- The affected employee
- The affected punch
- The correction action
- The original values
- The corrected values
- The correction reason
- The supervisor responsible
- The correction timestamp

Punch deletion requires an explicit typed confirmation.

Application audit records are also created for correction activity.

### Kiosk Inactivity Protection

The employee kiosk now automatically clears unfinished interactions after a configurable period of inactivity.

The timeout is managed under:

```text
Settings → Company Settings → Kiosk Safety
```

The allowed timeout range is:

```text
15–600 seconds
```

The default is:

```text
60 seconds
```

The inactivity system:

- Monitors keyboard activity
- Monitors mouse and pointer activity
- Monitors touch activity
- Monitors form input
- Displays a warning during the final 10 seconds
- Restarts the countdown when activity resumes
- Clears the selected employee
- Clears entered PIN data
- Clears temporary kiosk authentication
- Returns to the employee-number screen
- Does not automatically submit a punch

Server-side timeout validation prevents expired PIN or punch forms from being submitted after the browser timeout.

### Production Web Deployment

Version 0.6 has been validated under:

- Nginx

- SQLite
- Ubuntu Linux
- Cron
- Logrotate

The development PHP server is no longer required for production operation.

The production Nginx configuration:

- Disables Nginx version disclosure

### Dedicated Physical Kiosk

Version 0.6 includes a validated dedicated kiosk deployment using:

- LightDM
- Openbox
- Chromium
- A restricted `kiosk` Linux account
- Automatic login
- Full-screen browser kiosk mode
- Browser restart recovery
- Application-availability checks
- Hidden idle cursor
- Disabled screen blanking
- Disabled display power management
- Disabled system suspend, sleep, and hibernation

The local kiosk launches:

```text
http://127.0.0.1/kiosk
```

If Chromium exits unexpectedly, the kiosk launcher restarts it automatically.

If the web application is unavailable during startup, the launcher waits and retries until the kiosk responds.

### SQLite WAL Mode

The primary SQLite connection now configures:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 10000;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA wal_autocheckpoint = 1000;
```

WAL mode improves concurrency between:

- Employee kiosk requests
- Supervisor web requests
- Scheduled reports
- Backup operations
- Diagnostic commands

The database connection also creates SQLite sidecar files with group-writable permissions appropriate for the production web and console users.

Backup and restore workflows are WAL-aware.

### Log Rotation

Version 0.6 adds production log rotation for:

- Application logs
- Scheduler logs
- Cron logs
- Mail logs
- PHP-FPM application errors
- Physical-kiosk browser logs

Application logs are:

- Rotated daily
- Rotated when larger than 5 MB
- Retained for 30 rotations
- Compressed
- Recreated with application-appropriate permissions

Kiosk browser logs are retained for 14 rotations and use `copytruncate` so the persistent Chromium launcher can continue writing safely.

### Offline Frontend Assets

Bootstrap and Bootstrap Icons are now stored locally under:

```text
public/assets/vendor
```

The administration and kiosk interfaces no longer depend on an external content-delivery network for their primary frontend styles, scripts, or icons.

Vendored assets include:

- Bootstrap CSS
- Bootstrap JavaScript bundle
- Bootstrap Icons CSS
- Bootstrap Icons font files
- License files
- SHA-256 checksum manifest

Asset integrity can be checked from the project root with:

```bash
sha256sum --check public/assets/vendor/SHA256SUMS
```

This allows the kiosk interface to continue rendering correctly even when internet access is unavailable.

2. Pull or install the Version 0.6.0 source.
3. Install or update Composer dependencies if required.
4. Confirm that runtime directories are writable by the application user.
5. Run all pending database migrations:


6. Confirm migration history:

```bash
./iqwurks database:check
```

7. Confirm that migrations 010 and 011 are applied.
8. Open **Settings → Company Settings**.

- Manual weekly payroll email delivery
- Scheduled weekly payroll email delivery
- Scheduled exception-report delivery
- PDF or CSV email attachments
- Payroll-period approval
- Payroll-period locking
- Reopening approved payroll
- Supervisor review notes
- Payroll export profiles for third-party payroll systems
- A guided installation wizard
- An automated application-upgrade command
- Release packaging
- A universal per-command `--help` option
- Multiple companies
- Multiple physical locations
- Multiple independently managed kiosks

The default production deployment uses HTTP on a trusted local network. Installations requiring access across untrusted networks should add HTTPS before exposing the application.

A newly rotated mail log can temporarily cause the System Doctor to report a mail-activity warning until the next successful email delivery.
