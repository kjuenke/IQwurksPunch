# IQwurksPunch 0.8.0

**Release type:** Reporting automation, payroll email delivery, attachments, notifications, retry safety, and kiosk usability release
**Release version:** 0.8.0
**Release date:** July 31, 2026

---

## Overview

Version 0.8 expands IQwurksPunch reporting from basic daily payroll delivery into a more complete, auditable, and recoverable email-reporting system.

This release adds manual and scheduled weekly payroll reports, scheduled payroll-exception reports, payroll-approval notifications, operational-failure notifications, CSV and PDF payroll attachments, detailed delivery-attempt history, configurable retry policies, delayed automatic retries, retry-chain protection, malformed-record quarantine, attachment-size safeguards, and concurrency protection.

Daily, weekly, and exception-report deliveries can now be regenerated safely after eligible temporary failures. The retry system preserves the original reporting date, weekly reference date, schedule association, attempt count, and retry-chain relationship.

Failures that cannot be regenerated safely are marked permanently failed instead of being retried indefinitely.

Version 0.8 also improves the employee kiosk by allowing the Enter key to activate the available Clock In or Clock Out action after employee authentication.

This document describes the final Version 0.8.0 release. The release commit and Git tag are created after the final validation step.

## Highlights

### Manual Weekly Payroll Email Delivery

Version 0.8 adds manual weekly payroll email delivery.

Authorized supervisors can generate and send a weekly payroll report from the reporting interface.

The weekly report includes:

- The selected weekly reporting range
- Employee payroll totals
- Worked-hour totals
- Regular-time totals
- Overtime totals
- Payroll-period workflow metadata when applicable
- Company identity
- Company timezone
- CSV attachment
- PDF attachment

The weekly report uses the same payroll-calculation foundation as the Payroll Workspace and existing report exports.

Manual weekly delivery is recorded in email history and delivery-attempt history.

### Scheduled Weekly Payroll Delivery

Weekly payroll reports can now be delivered automatically.

A weekly schedule can define:

- Whether delivery is enabled
- The scheduled weekday
- The scheduled delivery time
- The applicable notification type
- The last delivery time
- The last delivery result

Scheduled delivery uses the configured company timezone.

Duplicate delivery protection prevents the same scheduled report from being sent repeatedly during subsequent scheduler runs.

Scheduled weekly reports preserve their schedule identifier in delivery history.

### Scheduled Payroll-Exception Reports

Version 0.8 adds scheduled delivery of open payroll-exception reports.

The exception report summarizes actionable, unresolved payroll exceptions from payroll periods that remain eligible for review.

Exception-report delivery includes:

- Actionable payroll periods
- Open exception totals
- Affected employees
- Exception descriptions
- Payroll-period context
- Review guidance

Resolved or accepted exceptions are excluded from the open-exception report.

Approved and locked payroll periods are not presented as actionable exception-report work.

The report can be delivered manually through its service layer or automatically through the scheduler.

### Exception-Retry Closure Messages

An exception report may fail while open exceptions exist but become eligible for retry after those exceptions have been resolved.

Version 0.8 handles this condition safely.

When an exception-report retry occurs:

- If open exceptions still exist, the current exception report is regenerated and sent.
- If no open exceptions remain, IQwurksPunch sends a short closure message instead of recreating an obsolete exception report.

The closure message confirms that the original exception condition has been resolved.

This closes the retry chain cleanly without sending stale payroll information.

### Payroll-Approval Notifications

Version 0.8 adds payroll-approval notifications.

When an authorized user successfully approves a payroll period, IQwurksPunch can notify recipients subscribed to:

```text
approval_notifications
```

The notification includes relevant approval information such as:

- Company name
- Payroll-period name
- Payroll-period range
- Approval user
- Approval timestamp
- Current workflow status

Approval notification delivery is separated from payroll-report subscriptions.

Recipients may subscribe to approval notifications without subscribing to daily or weekly payroll reports.

### Operational-Failure Notifications

Version 0.8 adds an operational-failure notification category.

Recipients may subscribe to:

```text
operational_failures
```

Automated and diagnostic workflows can use this notification type to report actionable operational failures.

Operational-failure notifications may include:

- The failing operation
- A human-readable failure explanation
- Relevant diagnostic context
- Exit or result information when available
- Recommended review guidance

Operational alerts are separated from routine payroll-report email.

This allows technical or administrative recipients to receive operational warnings without receiving payroll documents.

### Expanded Notification Center

The Notification Center now supports subscription control for:

```text
daily_payroll
weekly_payroll
exception_reports
approval_notifications
operational_failures
```

Each recipient may be enabled or disabled independently for each notification category.

Only active recipients subscribed to the selected notification type receive a message.

Unsupported notification types are rejected by the recipient repository instead of being inserted directly into a SQL query.

### CSV Payroll Attachments

Daily and weekly payroll emails now include CSV attachments.

CSV attachments are generated in memory during delivery and are not stored as permanent files under the runtime storage directories.

The attachment contains the applicable payroll-report information and uses a filename that preserves the report date or weekly reference date.

Daily attachment filenames follow the established pattern:

```text
iqwurkspunch-daily-payroll-YYYY-MM-DD.csv
```

Weekly attachment filenames preserve the weekly reporting reference date.

The stable filename format allows failed deliveries to recover their original reporting date safely during retry planning.

### PDF Payroll Attachments

Daily and weekly payroll emails now include PDF attachments.

PDF documents are generated from the same payroll information used by the email body and CSV attachment.

PDF attachments include appropriate company, reporting-range, payroll-total, and workflow information.

Like CSV attachments, PDF contents are generated in memory and are not archived automatically under `storage`.

Daily PDF filenames follow the established pattern:

```text
iqwurkspunch-daily-payroll-YYYY-MM-DD.pdf
```

### Shared Payroll Attachment Service

Version 0.8 adds a shared payroll-email attachment service.

The service centralizes creation of:

- Daily payroll CSV attachments
- Daily payroll PDF attachments
- Weekly payroll CSV attachments
- Weekly payroll PDF attachments
- Safe attachment filenames
- Attachment content types
- In-memory attachment contents

This prevents the manual and scheduled email paths from generating inconsistent attachment formats.

### Email Delivery Attempt History

Version 0.8 adds detailed email delivery-attempt history.

Each tracked delivery may record:

- Notification type
- Delivery source
- Subject
- Recipients
- Schedule identifier
- Status
- Attempt number
- Maximum attempts
- Parent retry identifier
- Permanent-failure state
- Error message
- Attachment count
- Attachment names
- Combined raw attachment size
- Start time
- Completion time
- Related email-history identifier

Supported delivery sources are:

```text
manual
scheduled
system
retry
```

Supported attempt statuses are:

```text
pending
sent
failed
```

The original delivery and each subsequent retry remain separate history records.

This preserves an auditable retry chain rather than overwriting the original failure.

### Scheduled Delivery Metadata

Scheduled daily, weekly, and exception-report emails now preserve their schedule identifiers in delivery-attempt history.

Delivery history can distinguish:

- Manual reports
- Scheduled reports
- System notifications
- Retry attempts

Scheduled attempt history also records the configured maximum-attempt count used by the retry policy.

### Retry Planning

Version 0.8 adds a dedicated retry-planning service.

The planner validates the failed attempt before allowing regeneration.

Validation includes:

- A valid delivery-attempt identifier
- Failed status
- Nonpermanent status
- Valid current attempt number
- Valid maximum-attempt count
- Remaining retry capacity
- Supported notification type
- Valid schedule metadata
- Valid attachment metadata
- Recoverable daily report date
- Recoverable weekly reference date

The planner preserves:

- Original failed-attempt identifier
- Notification type
- Schedule identifier
- Incremented attempt number
- Maximum attempts
- Retry-parent relationship
- Daily report date
- Weekly reference date

### Report-Date Preservation

Daily payroll retries preserve the original daily report date.

The retry planner obtains the date from the original attachment filename rather than regenerating a report for the current date.

This prevents a delayed retry from accidentally sending payroll data for the wrong day.

Weekly payroll retries similarly preserve the original weekly reference date.

### Retry Execution

Version 0.8 adds a dedicated retry-execution service.

Supported regenerable notification types are:

```text
daily_payroll
weekly_payroll
exception_reports
```

The execution service routes a validated retry plan to the correct report service.

The retry attempt is sent with:

- Source set to `retry`
- Original schedule identifier
- Incremented attempt number
- Original maximum-attempt count
- Original failed-attempt identifier as `retry_of_id`
- Preserved reporting date or reference date

### Payroll Email Retry Command

The console application now provides:

```bash
./iqwurks mail:retry
```

By default, the command runs in preview mode.

Preview mode:

- Displays eligible failures
- Displays the selection limit
- Displays the configured retry delay
- Displays the delivery type
- Displays the next attempt number
- Displays the schedule identifier
- Displays completion time
- Displays the original subject
- Does not send email
- Does not modify delivery records

To execute eligible retries:

```bash
./iqwurks mail:retry --send
```

An explicit selection limit may be supplied:

```bash
./iqwurks mail:retry --send --limit=10
```

The allowed explicit limit range is:

```text
1–250
```

### Configurable Retry Policy

Retry behavior is configured in:

```text
config/reporting.php
```

The Version 0.8 default policy is:

```php
'delivery_retry' => [
    'scheduled_max_attempts' => 3,
    'batch_limit' => 10,
    'delay_minutes' => 5
]
```

The original scheduled delivery counts as attempt 1.

A maximum-attempt value of 3 therefore permits:

- Original delivery
- First retry
- Second retry

The policy service validates configured values before they are used.

### Delayed Retry Eligibility

A failed delivery does not become eligible for immediate automatic retry.

The Version 0.8 default delay is:

```text
5 minutes
```

The eligibility service interprets SQLite completion timestamps consistently and excludes:

- Failures younger than the configured delay
- Permanent failures
- Attempts that reached their maximum
- Attempts that already have a child retry
- Attempts with malformed completion timestamps

This prevents rapid retry loops during temporary SMTP or network failures.

### Automatic Retry Cron

Production installations may run retry processing automatically with:

```cron
* * * * * cd /var/www/IQwurksPunch && /usr/bin/flock -n /tmp/iqwurks-mail-retry.lock /usr/bin/php iqwurks mail:retry --send >> storage/logs/cron-mail-retry.log 2>&1
```

The cron entry runs once per minute.

The configured retry delay determines when a failed delivery actually becomes eligible.

The external `flock` lock prevents overlapping cron executions.

### Internal Retry Lock

Version 0.8 also adds an application-level nonblocking retry lock.

The internal lock applies only to:

```bash
./iqwurks mail:retry --send
```

Preview mode remains unlocked and read-only.

The internal lock file is:

```text
/tmp/iqwurks-mail-retry.internal.lock
```

If another send-mode retry process is already running, the command exits safely without processing the same queue concurrently.

This protects retry execution even when the command is started outside the configured cron entry.

### Retry-Chain Protection

The retry repository returns only failed attempts that:

- Are not permanent
- Have remaining attempt capacity
- Have no existing child retry

Once any child retry exists, the original failed attempt is excluded.

This applies whether the child is:

- Pending
- Sent
- Failed

The same failed attempt therefore cannot produce duplicate retry children.

### Malformed Retry Quarantine

Malformed retry metadata is treated as a permanent data-quality failure.

Examples include:

- Missing attempt identifier
- Invalid attempt counts
- Invalid schedule identifier
- Missing daily report date
- Missing weekly reference date
- Invalid attachment metadata
- Unsupported notification type

When retry planning rejects a stored attempt, the original failure is updated with:

```text
permanent_failure = 1
```

The stored error begins with:

```text
Retry metadata is invalid:
```

Quarantined records are excluded from future automatic retry runs.

### Unsupported Retry-Type Quarantine

Only reports that can be regenerated safely are retried.

Approval notifications and operational-failure notifications represent event-driven messages and are not automatically recreated later.

Eligible records with unsupported notification types are no longer silently hidden by the console command.

Preview mode displays them without modification.

Send mode passes them to the retry planner, which marks them permanently failed with a clear explanation.

This prevents unsupported records from remaining indefinitely in the retry queue.

### Temporary Delivery Failures Remain Retryable

A delivery service returning `false` or throwing a temporary delivery exception does not automatically quarantine the attempt.

Ordinary SMTP and transport failures remain subject to the configured attempt limit.

A delivery becomes permanent when:

- The configured maximum-attempt count is reached
- Its retry metadata is invalid
- Its notification type cannot be regenerated safely
- Its attachment payload exceeds the configured size limit

### Attachment-Size Safety Limit

Version 0.8 adds a centralized combined attachment-size limit.

The default maximum raw attachment size is:

```text
10 MiB
```

The configuration value is:

```php
'email_attachments' => [
    'max_total_bytes' => 10485760
]
```

The raw-size ceiling leaves room for MIME encoding and message overhead before reaching common SMTP message-size limits.

The limit applies centrally in `MailService`, protecting daily, weekly, and future attachment-bearing email services.

Attachment size is checked:

1. After attachment normalization
2. After the delivery attempt has been recorded
3. Before the SMTP transport is created
4. Before any message is sent

An oversized delivery:

- Creates a failed email-history record
- Creates a failed delivery-attempt record
- Preserves attachment names and size
- Is marked permanently failed
- Is excluded from retry processing
- Does not contact SMTP

### Attachment Validation

Email attachments are normalized before delivery.

Validation includes:

- Attachment entry must be an array
- Filename is required
- Filename is reduced to a safe basename
- Control characters are removed
- Content type falls back to `application/octet-stream`
- Contents must be string data
- Empty contents are rejected
- Combined raw size must remain within policy

Attachment names and total raw size are recorded in delivery-attempt history.

## Known Limitations

Version 0.8 does not yet include:

- Employee time-card attachments in payroll email
- User-selectable attachment formats
- Automatic long-term attachment archiving
- A standalone delivery-attempt administration dashboard
- Multiple independently timed deliveries for the same report type
- Named recipient groups
- External payroll-provider export profiles
- Configurable third-party payroll field mappings
- A guided installation wizard
- An automated application-upgrade command
- Release packaging
- A universal per-command `--help` option
- Multiple companies
- Multiple physical locations
- Multiple independently managed kiosks

Automatic retry regeneration is intentionally limited to:

```text
daily_payroll
weekly_payroll
exception_reports
```

Event-driven approval and operational-failure notifications are not automatically regenerated because their original event context may no longer be current.

Email attachment contents are generated in memory and are not retained as permanent documents after delivery.

The configured attachment limit applies to raw attachment contents. MIME encoding and other message overhead increase the final transmitted message size.

The default production deployment continues to use HTTP on a trusted local network. Installations exposed to untrusted networks should add HTTPS before permitting remote access.
